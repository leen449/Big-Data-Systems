# Phase 5 report material (oral Q&A prep)

Not a results file -- `results/ml_metrics.txt` and `results/ml/*.csv` are the source of
truth and are regenerated by `sbt "runMain sonicspark.ml.MachineLearning"`. This file
pulls out the numbers, code, and explanations each teammate needs to talk through a
stage without re-reading the whole codebase. Confirmed deterministic: two full runs
produced byte-identical `ml_metrics.txt` (ignoring timing lines) and all 99 CSVs.

## 1. Split

**Key numbers:** 688 training recordings / 296 test recordings (70/30, stratified by
genre, seed 42). Per-genre train/test counts range 64-70 train and 28-30 test (metal has
only 64 train / 28 test recordings -- GTZAN's metal folder has fewer usable recordings
after cleaning). Disjointness check passed: no `track_id` in both sides. Gap pairs
excluded from the change features: 4 in train, 1 in test (Phase 4 found 5 across the
full dataset -- these are windows where cleaning removed a predecessor, so the LAG pair
isn't truly consecutive).

**Code (the seeded split core, `Split.scala`):**
```scala
val rng = new scala.util.Random(seed)
val splitRows: Seq[(String, String, String)] = byGenre.flatMap { case (genre, sortedTrackIds) =>
  val shuffled = rng.shuffle(sortedTrackIds)
  val numTrain = math.round(trainFrac * sortedTrackIds.size).toInt
  val (trainIds, testIds) = shuffled.splitAt(numTrain)
  trainIds.map(id => (id, genre, "train")) ++ testIds.map(id => (id, genre, "test"))
}
```

**Code (grouped fold assignment, `Split.scala`):**
```scala
val rng = new scala.util.Random(seed)
val foldRows: Seq[(String, String, Int)] = byGenre.flatMap { case (genre, sortedTrackIds) =>
  val shuffled = rng.shuffle(sortedTrackIds)
  shuffled.zipWithIndex.map { case (trackId, i) => (trackId, genre, i % numFolds) }
}
```

**Plain language:** We never let Spark decide which rows go where. Instead, on the
driver, we sort every recording's genre and track_id alphabetically (so the input
order never matters), shuffle with one seeded random-number generator, and cut the
list 70/30. The same technique assigns each training recording a fold number 0-4.
Because splitting happens at the *recording* level, every one of a recording's ~59
overlapping windows stays together -- a model can never see some of a song's windows in
training and the rest in testing, which would let it "cheat" by recognizing the
specific recording instead of learning genre.

## 2. Train-only feature analysis

**Key numbers:** All 38 final-dataset features recomputed on training windows only.
Nothing dropped beyond `spectral_centroid_mean` (already removed by Phase 2). Highest
η²: `log_flatness_var` (0.494), `log_rms_var` (0.488), `mfcc1_mean` (0.476). 12 pairs
with |r| > 0.8 reported (none beyond the already-known `spectral_bandwidth_mean`/
`rolloff_mean` pair at 0.95, which is below our 0.95 action threshold so nothing new
is dropped). Phase 2 recheck (on `data/interim/02_integrated`, train recordings only):
r(spectral_centroid_mean, rolloff_mean) = 0.967, η²=0.374 vs 0.422 -- Phase 2's decision
still agrees under train-only statistics.

**Code (η² — identical formula to Reduction.scala, reimplemented independently in `FeatureAnalysis.scala`):**
```scala
def etaSquared(df: DataFrame, cols: Seq[String], n: Long): Map[String, Double] = {
  val overall = df.agg(/* avg + var_pop per feature */).head()
  val genres  = df.groupBy("label").agg(/* count + avg per feature */).collect()
  cols.map { c =>
    val between = genres.map(g => g.getAs[Long]("n") * math.pow(g.getAs[Double](c) - mean, 2)).sum
    c -> (between / total)
  }.toMap
}
```

**Plain language:** η² (eta-squared) asks "if I only knew a window's genre, how much
of this feature's total variation could I explain?" We recompute it on training
windows only (never test windows) so that no decision about which features to use is
contaminated by data the model will later be judged on. We also redo Phase 2's specific
removal of `spectral_centroid_mean` with train-only numbers, as an audit -- it still
agrees, so Phase 2's full-dataset-derived decision wasn't accidentally leaking test
information.

## 3. Extra features

**Key numbers:** `range_p95_p5` (η²=0.419), `d_loudness_mean_abs` (0.292),
`d_mfcc1_mean_abs` (0.198), `d_bandwidth_mean_abs` (0.145) -- all four candidate columns
are at least as genre-informative as the median base feature. LogisticRegression's
grouped-CV-winning feature set was **F3** (+range +change); RandomForest's was **F2**
(+change only). Decision made purely from CV score, before any test evaluation.

**Code (`ExtraFeatures.scala`, Q2-style robust range, grouped by `track_id` not genre):**
```scala
def robustDynamicRange(windows: DataFrame): DataFrame = {
  val withLoudness = windows.withColumn("loudness_db", lit(20.0) * log10(col("rms_mean") + AudioConfig.Epsilon))
  withLoudness.groupBy("track_id").agg(
    (percentile_approx(col("loudness_db"), lit(0.95), lit(10000))
      - percentile_approx(col("loudness_db"), lit(0.05), lit(10000))).as("range_p95_p5")
  )
}
```

**Plain language:** These two features are ported straight from Phase 4's SQL
(Q2's p95-p5 loudness range, Q4's consecutive-window change), just aggregated per
*recording* instead of per genre. Because each value only ever uses that one
recording's own windows, computing them for test recordings too is not leakage -- no
label and no other recording's data is involved. The real risk is different: since the
value is identical across all of a recording's windows, a model could "memorize" which
recording produced which value instead of learning genre. Grouped CV is exactly what
would catch that (a fingerprinted value from training recordings is useless on
recordings the model has never seen a single window of) -- and since both extra
feature sets won fair and square under grouped CV, we trust the lift is real.

## 4. Cross-validation

**Key numbers:** Stage 1 (LR 3-config × RF 1 fixed config, × 4 feature sets, 5-fold
grouped CV): 1600-1650s (~27 min) across both runs. Stage 2 (RF numTrees×maxDepth grid
on RF's winning feature set only): ~2050s (~34 min). LR's best: regParam=0.001 on F3
(CV weighted-F1=0.600). RF's best: numTrees=150, maxDepth=12 on F2 (CV weighted-F1=
0.575). **Limitation:** RF grid trimmed from the planned {100,200}×{10,15} to
{100,150}×{10,12} after the heaviest config caused repeated `OutOfMemoryError` crashes
(two different failure modes, ~2 hours of wall time each) in the out-of-fold loop on
this machine's ~12GB RAM -- a hardware constraint, decided before any test-set result
was seen, not a modelling choice.

**Code (`ModelTraining.scala`, grouped CrossValidator -- the leakage guard is `setFoldCol`):**
```scala
val grid = new ParamGridBuilder().addGrid(lr.regParam, MlConfig.LrRegParams.toArray).build()
val cv = new CrossValidator()
  .setEstimator(buildPipeline(cols, lr)).setEvaluator(evaluator).setEstimatorParamMaps(grid)
  .setFoldCol(MlConfig.FoldColName).setNumFolds(MlConfig.NumFolds).setSeed(MlConfig.Seed)
val cvModel = cv.fit(trainDf)
```

**Code (assembler/scaler/classifier pipeline, `ModelTraining.scala`):**
```scala
def buildPipeline(featureCols: Seq[String], classifier: PipelineStage): Pipeline = {
  val assembler = new VectorAssembler().setInputCols(featureCols.toArray).setOutputCol("features")
  val scaler = new StandardScaler()
    .setInputCol("features").setOutputCol("scaledFeatures").setWithMean(true).setWithStd(true)
  new Pipeline().setStages(Array(assembler, scaler, classifier))
}
```

**Plain language:** `setFoldCol` is the single most important line in this project for
avoiding leakage during model selection. Spark's default cross-validation would split
*rows* randomly into folds -- since a recording's ~59 windows are 50%-overlapping and
nearly identical, that would let windows from the same recording sit in both the
training and validation side of a fold, inflating every score. `setFoldCol` instead
uses our own `cv_fold` column (assigned per *recording* in Split.scala), so a fold
boundary always falls between whole recordings. The pipeline itself is simple: turn the
chosen feature columns into one vector, standardise it (zero mean, unit variance, fit
on that fold's training rows only), then classify.

## 5. Final fit and interpretation

**Key numbers:** Final LR and RF models are literally `CrossValidator`'s own
best-configuration refit on all 688 training recordings (reused directly, not refit a
third time). RF feature importance: top 4 are all extra/engineered features
(`d_loudness_mean_abs` 0.091, `rms_mean` 0.077, `d_mfcc1_mean_abs` 0.066,
`d_bandwidth_mean_abs` 0.064). LR's top positive feature for blues: `mfcc3_mean`
(+0.839); top negative: `log_flatness_var` (-0.871).

**Plain language:** We don't fit a third "final" model -- `CrossValidator` already had
to refit the winning configuration on the entire training set internally (that's how
Spark reports `bestModel`), so reusing that object means "the model we evaluate" and
"the model CV selected" can never silently drift apart. RF's feature importance being
dominated by the engineered change features doesn't contradict the leakage story above:
importance measures how much a feature helps fit the *training* data, while CV score
measures whether that help generalizes to recordings never seen during training -- both
can be true at once.

## 6. Grouped out-of-fold evaluation and soft voting

**Key numbers:** A genuine 5-fold loop (fit on 4 folds, predict the 5th, union) is run
for LR, RF, and all three baselines with their final chosen configuration -- 25 extra
fits. This is what fills the "oof" rows in `metrics_summary.csv`: real held-out
predictions, not just a `CrossValidator` average score.

**Code (`ModelTraining.scala`, the generic OOF loop):**
```scala
def runGroupedOof[M](trainDf: DataFrame, foldCol: String, numFolds: Int,
                      fitFn: DataFrame => M, predictFn: (M, DataFrame) => DataFrame): DataFrame = {
  val perFoldPredictions = (0 until numFolds).map { fold =>
    val foldTrain   = trainDf.filter(col(foldCol) =!= fold)
    val foldHoldout = trainDf.filter(col(foldCol) === fold)
    predictFn(fitFn(foldTrain), foldHoldout)
  }
  perFoldPredictions.reduce(_ unionByName _)
}
```

**Code (soft voting, `MlMetrics.scala`):**
```scala
def softVoteToRecording(windowPreds: DataFrame): DataFrame = {
  val recordingProbs = windowPreds.groupBy("track_id")
    .agg(first("label_idx").as("label_idx"), Summarizer.mean(col("probability")).as("probability"))
  val argmaxUdf = udf((v: Vector) => v.toArray.zipWithIndex.maxBy(_._1)._2.toDouble)
  recordingProbs.withColumn("prediction", argmaxUdf(col("probability")))
}
```

**Plain language:** `runGroupedOof` is the same idea as the CV search, but instead of
just keeping a score, we keep the actual predictions on the held-out fold every time,
so by the end every training recording has a prediction made by a model that never saw
it. That's the fairest "almost-test" number we can report on training data. Soft voting
then takes a model's per-window class-probability guesses for one recording, averages
them into a single probability vector, and picks the most likely genre -- so a
recording's final verdict reflects the whole excerpt, not just one window.

## 7. Metrics and the sanity check

**Key numbers (test set, recording-level soft voting):** Majority 0.1014 acc / 0.0184
macro-F1. CentroidPlain 0.5236 / 0.4956. CentroidPCA 0.6453 / 0.6422. LR **0.7027** /
0.7045. RF 0.6824 / 0.6845. Note RF's train accuracy is 0.9927 (recording-level) --
massive overfitting that only shows up once you compare it against OOF (0.6308) and test
(0.6824); this is exactly why the task requires reporting train/OOF/test separately
instead of just train accuracy. Metal recall: LR 0.893, RF 0.821, CentroidPCA 0.893 --
all above the cross-genre average (0.61-0.68). Sanity check: hand-counted accuracy
(0.619143) matches `MulticlassClassificationEvaluator`'s accuracy (0.619143) exactly,
for LR window-level test predictions.

**Plain language:** We compute accuracy/macro-F1/weighted-F1/confusion matrices by
plain counting rather than Spark's `MulticlassMetrics` (which doesn't expose macro-F1
either), specifically so every teammate can read the formula directly in
`MlMetrics.scala` instead of trusting a library black box. The one sanity check (hand
count vs. Spark's own evaluator, same predictions) exists purely to prove that
hand-rolled code isn't silently wrong -- and it matched exactly.

## Limitations to state plainly in the write-up

- The RF hyperparameter grid is narrower than planned ({100,150}×{10,12} instead of
  {100,200}×{10,15}) due to repeated out-of-memory crashes on this machine's ~12GB RAM.
  This was fixed before any test-set evaluation, so it does not bias the test result,
  but it does mean RF's search was less thorough than LR's.
- Do not claim that aggregating window predictions into a recording-level vote gives the
  model access to "long-term dynamics" -- nothing in the outputs demonstrates that; soft
  voting is only an averaging of independent per-window guesses.
